# game_platform — продуктовый документ (PM)

Версия 0.1 · 2026-09-29 · основа: `docs/opportunity-map.md`, `docs/platform-architecture.md`, код `packages/*` на 29.09 17:05, эталон `QmaCyber/game`

**Продукт** — не движок, а **комплект**: правила + готовые блоки + инструменты + документы + процессы, с которыми агент проходит путь «бриф в одну строку → игра, готовая к публикации» быстро и без потери качества. Детские игры — первый набор (kit), а не граница продукта.

**Северная метрика:** время от брифа до пакета для публикации (AAB + листинг + графика + privacy + чек-лист) при зелёном QA. Эталон: ≈4 ч и одна AI-сессия (Balloon Pop).

## 4. Бэклог (топ-15, по приоритету)

Правило из opportunity-map §16: каждая задача отвечает на вопрос «какую гипотезу это проверяет?». ⚠️ — риск overengineering, в скобках — как его ограничить.

| # | Задача | Гипотеза → метрика | Веха | Риск |
|---|---|---|---|---|
| 1 | `gp` CLI минимум: `validate`, `explain`, `catalog` c `--json` (данные уже в `spec`) | ошибки с `fix` дают исправление за 1 итерацию → ≥ 80% с первой попытки | M0 | — |
| 2 | Перенести `qa.mjs` → `packages/qa`, опираясь на события; `gp qa` | паритет доказывается тем же тестом → 74/74 | M0 | ⚠️ не делать «QA-фреймворк»: сначала 1:1 порт, профильные правила — потом |
| 3 | Юнит-тесты: `ads.test.ts`, resolve/validator (по тесту на код ошибки) | правила нельзя ослабить незаметно → 0 регрессий | M0 | — |
| 4 | `gp build android` + CI сборки AAB + device-test на эмуляторе | браузерного QA мало (5 падений на эмуляторе у эталона) → 31/31 | M0 | — |
| 5 | Генерация `game.schema.json` + справочник (поля, каталог, ошибки) + `gp docs --check` в CI | сгенерированные документы не расходятся с кодом (ручные уже разошлись, §1.4) → 0 расхождений в CI | M0 | ⚠️ без сайта документации: только markdown в репо |
| 6 | Проверка всех YAML-примеров в документации в CI; исправить архитектуру §2.1, §6 | пример, который не проходит `validate`, — баг → 0 невалидных примеров | M0 | — |
| 7 | `AGENTS.md` v0 (1 страница) + 3 стартера `game.yaml` | агенту хватает одной страницы → ≤ 3 вопросов без ответа на M1 | M0→M1 | ⚠️ одна страница, не больше |
| 8 | Реестр механик и траекторий: `round` выбирает схему по `mechanic`, `trajectory.type` (сейчас захардкожено) | спецификация расширяется без правки `core` → 0 изменений `core` на M1 | M1 | ⚠️ ровно два варианта (`tap-collect`+`rise`/`fall`, `jar`), без «плагинной системы» |
| 9 | Блоки для Catch a Star: `fall`, `jar`, `night-sky`, `shapes-en`, `stickers-space` — каждый по DoD | новая игра = изменения, а не проект → M1.1 < 2 ч | M1 | — |
| 10 | `gp preview --scene --mode --seed --shot` | визуальный цикл сокращает итерации → правка → скриншот < 10 с | M1 | ⚠️ `--gallery` и hot reload — только если агент просит |
| 11 | Store kit: шаблон листинга + `gp listing check`, privacy policy из профиля канала, store-art из темы | «хвост» после кода — около половины работы → от зелёного QA до пакета стора < 30 мин | M1 | — |
| 12 | Чек-лист публикации по каналу (генерируется) + `gp release check` (все `TODO(publisher)`, ID, версия, подпись) | издатель тратит меньше часов → ≤ 2 ч человека на игру без учёта ожидания Google | M1 | ⚠️ не автоматизировать Play Console API |
| 13 | Журнал сессии агента: время, итерации, вопросы без ответа, токены (шаблон `REPORT.md` + счётчики `gp`) | без замера M1 не доказать → все метрики M1 заполнены | M1 | ⚠️ файл-отчёт, не телеметрия и не дашборд |
| 14 | Golden-скриншоты эталонных игр в CI | новый блок не ломает старые игры → 0 регрессий | M1 | — |
| 15 | Проверка «не повтор» (Repetitive Content): сравнение с другими `games/*` по механике, теме, контенту и листингу | один бан снимает весь портфель → 0 отказов модерации по спаму | M1 | ⚠️ сначала пункт чек-листа, код — если игр ≥ 4 |

**Сознательно не делаем до M3 (overengineering):** MCP-сервер (есть `gp --json`), `extends:` и `gp upgrade`, сайт документации и `llms.txt`, автоматизация `gp admob provision` через API (хватит ручного шага с готовыми именами), `gp doctor`, hot reload, локализация (эталон только на английском), `edu-kit`/`casual-kit`, аналитика в играх (до решения по Data safety), визуальный редактор.

## 5. Вопросы

### Вопросы к геймдизайнеру

1. **Минимальное отличие игр** для политики Repetitive Content: что обязательно менять — механику, траекторию или достаточно темы + контента + листинга? Нужна формулировка, которую можно превратить в правило чек-листа (бэклог №15).
2. **Catch a Star, `jar`:** что происходит с непойманной звездой (просто исчезает — «без проигрыша» для 2–5)? Режим «счёт» озвучивает порядковый номер пойманной звезды («one, two, three…») или число на звезде? `goal` = 12 или 15?
3. **Качество «ощущения», которое QA не видит:** назовите 3–5 измеримых критериев хорошей детской игры (первая награда ≤ N с, раунд 30–60 с, не больше K целей одновременно, темп появления), чтобы проверять их по `game.events`.
4. **Темы:** можно ли большинство из 7 игр GDD §12 сделать темой-данными (палитра, эмодзи или SVG цели, фон из слоёв), или каждой нужна своя отрисовка в коде? От ответа зависит, сможет ли агент делать тему без разработчика.
5. **Мета-цикл kids:** звёзды + наклейка + альбом одинаковы во всех детских играх или нужны варианты (без альбома, другой размер альбома, другой экран награды)?
6. **Первая «не детская» игра:** какая и когда? M2 — умножение для 6–8, но продукт заявлен шире детей: нужен ли `general`-эталон раньше M4?

### Вопросы к аналитику

1. Какую гипотезу из MVP A–E платформа обслуживает в ближайшие 45 дней? От этого зависит, что важнее после M1: упаковка Android или web/playable (MRAID).
2. **Северная метрика «быстро»:** что считаем — время сессии агента, часы человека, токены/$ или всё вместе? Какая базовая линия у Balloon Pop по каждой (4 ч включают документы и графику стора?).
3. В играх нет аналитики (Data safety). Как будем мерить установки и D1 для MVP A: только статистика Play Console и AdMob? Нужен ли когда-нибудь слой `events → analytics`?
4. Если M1 даст 2,5–3 ч вместо < 2 ч: это провал гипотезы или приемлемо? Какой порог «платформа окупилась» против подхода «копировать репозиторий эталона»?
5. Проверена ли поддержка Казахстана для Play merchant и выплат AdMob? Если нет — считаем ли `remove_ads` частью M1?
