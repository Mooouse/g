## 0. Кратко: проверка концепции и бизнес-модели

### 0.1 Что уже доказано кейсом Balloon Pop

| Вопрос | Факт из репозитория `game` |
|---|---|
| Может ли AI собрать законченную детскую игру? | Да. HTML5 Canvas + TypeScript + Capacitor 8, 4 режима, альбом наклеек, родительский замок, AdMob с правилами Families, покупка `remove_ads`, 8 unit-тестов, 74/74 браузерных QA-проверок, CI-сборка AAB, эмулятор-тест, GDD, privacy policy, тексты и графика для стора |
| Сколько это стоило по времени? | 17 коммитов, от первого до последнего **≈4 часа** (29.09.2026, 11:39 → 15:55) в одной AI-сессии |
| Есть ли основа для шаблона? | Да. `src/theme.ts` (визуал и механика тапа), `src/config.ts` (баланс и лимиты рекламы), `src/i18n.ts` (контент) — это уже неявная «спецификация игры». В GDD §12–13 есть 7 следующих игр на этом шаблоне и чек-лист «новая игра из шаблона» |
| Что осталось ручным? | Всё, что касается магазина: аккаунт, D-U-N-S, создание приложения в Play Console, IARC, Data safety, 12 тестеров × 14 дней (личный аккаунт), AdMob, `app-ads.txt`, проверка на устройстве. См. `docs/play-console-checklist.md`: 3–5 недель календарного времени |

**Вывод 1.** Главная техническая гипотеза («предельная стоимость следующей игры намного ниже традиционной») для простых шаблонных игр **уже почти подтверждена**. Производство перестало быть узким местом. Строить большую платформу, чтобы доказать это ещё раз, не нужно.

### 0.2 Экономика исходной гипотезы «фабрика детских игр → пассивный доход»

Опорные цифры рынка (2026):
- Детские/образовательные приложения: US interstitial eCPM $4–8, **ARPDAU $0.02–0.05**. С COPPA-трафиком (без персонализации) реклама платит на 60–80% меньше. Обновлённое правило COPPA действует с 22.04.2026, спрос на COPPA-инвентарь сжимается.
- Balloon Pop сознательно показывает мало рекламы: не раньше 2-го раунда, не чаще раза в 2 раунда и 90 с. Это правильно для Families-политики, но ARPDAU будет у нижней границы диапазона.

Юнит-экономика одной игры **[гипотеза]**:

```
Доход в месяц ≈ DAU × ARPDAU × 30 ≈ DAU × $0.9        (ARPDAU = $0.03)
LTV игрока   ≈ ARPDAU × ожидаемые дни жизни ≈ $0.03 × 6 ≈ $0.18
             + remove_ads: $2.99 × 0.7 × (0.3–1% конверсии) ≈ $0.01–0.02
             ⇒ LTV ≈ $0.2
Затраты      ≈ запуск 6–10 ч человека (стор, тесты) + AI-токены $20–100
             + обслуживание 2–4 ч/год (targetSdk каждый август,
               Billing Library, сертифицированный Ads SDK, политики)
```

Порог окупаемости низкий: при $20/ч игре нужно в среднем **~20–30 DAU** в первый год. Но:

| Фактор | Оценка | Почему |
|---|---|---|
| Стоимость производства | ✅ низкая | доказано кейсом |
| Доход на пользователя | ⚠️ очень низкий | LTV ≈ $0.2: **платный трафик почти наверняка не окупится**, остаётся только органика и ASO |
| Distribution | ❌ главный неизвестный | в сторе результаты распределены по степенному закону: большинство новых игр получают почти ноль установок. Средняя игра, а не лучшая, должна набрать 30+ DAU |
| Масштабирование «×1000» | ❌ заблокировано политикой | Google Play Spam/Repetitive Content запрещает почти одинаковые приложения. GDD Balloon Pop сам ограничивает выпуск: не чаще раза в 2–4 недели, у каждой игры своя механика. Бан аккаунта снимает **весь портфель сразу**, риск коррелирован |
| «Пассивность» | ⚠️ полупассивно | ежегодные обязательные обновления × N игр, модерация, отзывы, изменения политик |
| Платёжная инфраструктура | ⚠️ проверить | в чек-листе отмечено: нужно проверить, поддерживается ли Казахстан для Play merchant и выплат AdMob |

**Вывод 2.** Модель «много детских игр в Google Play на рекламе» **технически жизнеспособна, но экономически слабая и плохо масштабируется**. Её ограничивает не производство, а (1) доход на пользователя, (2) органическая дистрибуция, (3) политика стора. Проверять её стоит дёшево, на 3 играх, а не строить под неё платформу.

**Вывод 3.** Та же технология (HTML5-runtime + шаблоны + AI-агенты + автоматический QA) даёт в B2B-нишах доход **в 100–1000 раз больше на единицу продукции**. Playable ads стоят $3–8k за штуку при внешнем производстве, брендовые мини-игры $500–5000, образовательные подписки ~$60/год на учителя. Эти варианты нужно проверять параллельно, а не после.

**Главный вопрос для следующего шага:** не «можем ли мы сделать игру» (можем), а **«в каком канале средняя игра, сделанная за 4 часа, окупает эти 4 часа»**.

### 0.3 Центр идеи: библиотека, в которой AI-агенту удобно делать игры

Суть проекта — не «фабрика» и не «ещё один движок», а **библиотека + инструменты, рассчитанные на агента, а не на человека**. Человек-разработчик терпит неявные соглашения, агент — нет. Ему нужны явные контракты, быстрая обратная связь и машиночитаемые ошибки.

**Что Balloon Pop показал о потребностях агента.** Агент справился за ≈4 часа, но заново написал то, что будет одинаковым в каждой игре: цикл кадров, DPR, safe-area, мультитач, родительский замок, правила рекламы, Billing с подтверждением покупки, Android-манифест, CI, QA-скрипт, генерацию графики стора. Большая часть найденных багов (двойной `finishRound`, потерянное подтверждение покупки, реклама после паузы) — в этой общей части. Библиотека должна забрать всё это у агента **один раз и навсегда**, чтобы агент писал только то, что отличает игру.

**Принципы agent-friendly библиотеки:**

| Принцип | Что это значит на практике |
|---|---|
| Маленькая поверхность API | ~10–20 точек расширения (механика, генератор контента, тема, награда), а не сотни классов |
| Спецификация вместо кода, где возможно | `GameSpec` (JSON Schema): агент заполняет данные, а не пишет логику |
| Типы и схемы как документация | TypeScript-интерфейсы + JSON Schema; невалидное состояние невыразимо |
| Ошибки с подсказкой исправления | `E_TOUCH_TARGET: target.radius=30 < 38 (ages 2–5). Fix: set mechanic.targetSize ≥ 38` — агент чинит за одну итерацию |
| Быстрый цикл «изменил → увидел» | headless-запуск, скриншот каждой сцены, лог событий за секунды: `game preview`, `game qa` |
| Детерминизм | seed для RNG, фиксированное время в тестах; одинаковая спецификация даёт одинаковую игру |
| Compliance встроен | Families/COPPA-лимиты — дефолты, которые нельзя ослабить без явного флага и ревью |
| Документация для агента | `AGENTS.md` / `llms.txt`: правила, каталог компонентов, 3–5 эталонных игр как примеры |
| Инструменты через MCP | `validate`, `build`, `preview`, `qa`, `package` как MCP-tools: работает с Claude Code и любым агентом |
| Песочница | компонент не имеет доступа к сети и хранилищу напрямую, только через API runtime (ads/IAP/storage) |
| Версионирование компонентов | `tap-targets@1`: старые игры не ломаются при развитии библиотеки |

**Черновая структура библиотеки** (вырастает из кода Balloon Pop, не пишется с нуля):

```
packages/
  runtime/      цикл кадров, сцены, ввод, аудио/TTS, storage       ← src/app.ts, audio.ts, storage.ts
  kids-kit/     parent gate, ads-правила Families, remove_ads      ← src/scenes/parent.ts, ads.ts, billing.ts
  components/   механики: tap-targets, tap-correct-answer, drag…   ← src/field.ts, scenes/play.ts
  spec/         GameSpec JSON Schema + семантический валидатор     ← config.ts/theme.ts/i18n.ts
  qa/           профили QA по возрасту и каналу                    ← tools/qa.mjs, device-test.mjs
  packager/     android (Capacitor) · web · playable · store-art   ← android/, tools/make-art.mjs
  mcp-server/   validate · build · preview · qa · package
  AGENTS.md     как агент делает новую игру
games/
  balloon-pop/  spec.yaml (+ компоненты, если их нет в библиотеке)
```

**Метрики библиотеки** (по ним видно, что она действительно помогает агенту):
- время от брифа до зелёного QA (сейчас ≈4 ч → цель < 1 ч);
- число итераций до валидной спецификации (цель ≤ 2);
- доля игр, собранных **без нового кода**, только из спецификации;
- число дефектов, найденных на устройстве после зелёного QA (цель 0).

**Бизнес-проверка идеи «библиотеки».** У библиотеки два пути, и проверять их нужно в таком порядке:
1. **Внутренний инструмент.** Ценность библиотеки = экономика игр и B2B-продуктов, которые на ней выпускаются (концепции ниже). Это единственный способ доказать, что она работает.
2. **Продукт для внешних разработчиков** (концепция 15: SDK/API/MCP-сервер). Рынок AI-генерации игр переполнен (Rosebud AI, генераторы в AppLovin/Meta/Unity), а у библиотеки без дистрибуции слабый moat. Возможная ниша — **«compliance-ready kids/edu kit для агентов»** или open-source ядро + платные компоненты/сервисы. Этот путь стоит проверять только после того, как на библиотеке выпущено 3–5 игр, которые приносят доход.

Итог: библиотека — правильное ядро проекта, но **её спецификацию определяют реальные игры**. Строим её, извлекая общий код при выпуске игр №2 и №3, а не проектируя заранее.

## 1. Technology thesis

AI-агенты надёжно собирают игры, если пространство решений ограничено:
1. **Runtime** — проверенный HTML5-движок (Canvas/TypeScript), общий для всех игр: сцены, ввод, звук, сохранения, реклама, покупки, родительский замок.
2. **Спецификация игры** — декларативный JSON/YAML (GameSpec), который агент пишет и который автоматически валидируется.
3. **Реестр компонентов** — механики, генераторы контента, награды. Новая механика = новый компонент с тестами, а не новая игра с нуля.
4. **Автоматический QA** — как `tools/qa.mjs`: размеры экранов, touch-таргеты, fps, мультитач, правила рекламы, compliance.
5. **Упаковка под канал** — Android AAB, web-портал, playable ad (MRAID), SCORM для корпоративного обучения, embed для сайта.

Преимущество не в том, что AI «пишет игры». Это уже commodity: Rosebud AI (Series A $15M), встроенные генераторы у AppLovin/Meta/Unity для playables. Преимущество — в **производственной системе, которая стабильно выдаёт соответствующие политикам игры, прошедшие QA, для конкретного канала**, плюс в данных о том, что работает.

## 6. Где AI-автоматизация даёт максимальное экономическое преимущество

Формула: **преимущество ≈ (цена рынка за единицу − наша себестоимость) × частота запросов**, при условии, что дистрибуция не съедает разницу.

| Ситуация | Традиционная цена | Себестоимость фабрики [гипотеза] | Разрыв |
|---|---|---|---|
| Playable ad (вариант) | $3–8k | $20–100 + 1–3 ч | ×30–100 |
| Брендовая мини-игра на шаблоне | $500–5000 | $20–100 + 2–6 ч | ×5–30 |

«Слишком мало для традиционной разработки, но достаточно, чтобы окупить автоматизацию»: **playables, брендовые мини-игры, локальные языки, специализированные упражнения (логопедия)**.

## 7. Competitive barriers и potential moats

Слабые moats (копируются за недели): сам DSL, шаблоны, отдельная игра, промпты.

Потенциально сильные moats:
1. **Compliance как код**: Families, COPPA 2026, Apple Kids, GDPR-K встроены в валидатор и CI (сейчас это уже частично есть: CI валит сборку при появлении `AD_ID`, тесты запрещают ослаблять лимиты рекламы). Конкуренту нужно повторить всю систему, а не одну игру.
2. **Данные о результатах**: какие темы, механики и иконки дают установки и удержание. Накапливается только с портфелем.
3. **Библиотека проверенных компонентов** с тестами: каждая новая игра удешевляет следующие.
4. **Аккаунты и репутация**: Play-аккаунт организации с историей, Teacher Approved, отзывы родителей.
5. **B2B-отношения и интеграции**: партнёры, телеком-бандлы, школы. Долгий цикл продажи защищает, когда контракт уже подписан.
6. **Локальный контент и озвучка** на малых языках.

## 9. Product factory: действительно ли нужно «×1000»?

- **Kids / Play:** нет. Политика Repetitive Content и коррелированный риск бана ограничивают выпуск ~1 игрой в 2–4 недели. Выигрывают **меньше игр, но лучше** (удержание, отзывы, Teacher Approved) и **одно приложение-хаб** с играми как контентом (концепция 2): ограничение на количество приложений снимается, обновления делаются один раз.
- **Порталы:** объём ценится умеренно (CrazyGames), Poki выбирает качество. Насыщение наступает быстро, если игры похожи.
- **B2B (playables, брендовые):** здесь «×1000 вариаций» действительно ценно: A/B-тесты креативов требуют десятков вариантов, каждый клиент хочет свой бренд.
- **Поддержка портфеля:** в N отдельных приложениях каждое ежегодное требование (targetSdk, Billing, Ads SDK) стоит × N. **Монорепо + один runtime + batch-обновления через Publishing API** — обязательное условие, иначе поддержка съедает доход.
- **Устаревание:** детские механики живут годами (evergreen), playables — неделями (creative fatigue). Поэтому B2B-вариации = постоянный спрос.

## 10. Уровни автоматизации

| Уровень | Что | Экономическая ценность | Статус |
|---|---|---|---|
| L1 | AI помогает разработчику | низкая, commodity | — |
| L2 | AI делает компоненты | средняя | — |
| L3 | AI делает игру целиком | высокая | ✅ Balloon Pop |
| L4 | AI делает и тестирует | **максимальная для MVP** | ✅ частично (qa.mjs, unit, emulator CI) |
| L5 | AI публикует | средняя: обновления автоматизируются, создание новой игры в Play — ручное; порталы и B2B-доставка — да | ⚠️ полуавтомат |
| L6 | AI анализирует метрики и выпускает следующую версию | высокая, **но только когда есть трафик** | ❌ преждевременно |
| L7 | Полная фабрика | — | ❌ после доказанной экономики |

**MVP = L4 + полуавтоматический L5.** Человек остаётся издателем: аккаунты, ревью политик, финальный клик публикации.

## 11. DSL и API: подходы

| Подход | Удобство для AI | Детерминизм | Валидация | Тестирование | Безопасность | Производительность | Сложность разработки | Расширяемость | Вердикт для MVP |
|---|---|---|---|---|---|---|---|---|---|
| A. DSL → компилятор → движок | среднее (новый синтаксис) | высокий | высокая | высокая | высокая | высокая | **высокая** | средняя | преждевременно |
| B. DSL → интерпретатор | среднее | высокий | средняя | высокая | высокая | средняя | средняя–высокая | средняя | позже |
| C. JSON/схема-спецификация | **высокое** (LLM знают JSON Schema) | высокий | **высокая** (schema + семантические правила) | высокая | высокая (нет произвольного кода) | высокая | **низкая** | через реестр компонентов | ✅ старт |
| D. Component API (TypeScript) | высокое | средний | типы TS | высокая | средняя (код) | высокая | низкая | **высокая** | ✅ для новых механик |
| E. Гибрид C + D | высокое | высокий | высокая | высокая | контролируемая | высокая | средняя | высокая | ✅ целевая архитектура |
| F. LLM-friendly декларативный язык | высокое | высокий | высокая | высокая | высокая | высокая | средняя | средняя | это C + хорошие примеры и ошибки |

**Рекомендация: E, эволюционно.**
1. **Не проектировать DSL заранее.** Взять `theme.ts + config.ts + i18n.ts` из Balloon Pop и вынести их в `GameSpec` **при создании игры №2**. Обобщать — после игры №3 («правило трёх»).
2. Спецификация = JSON/YAML + JSON Schema + **семантический валидатор** (возрастные правила, лимиты рекламы, touch-таргеты, уровень чтения, длительность сессии).
3. Если механики нет в реестре — агент пишет TypeScript-компонент по Component API, компонент проходит тесты и ревью, потом попадает в реестр. Так DSL растёт вместе с реальными играми.

Пример запроса пользователя и спецификации, в которую его переводит Designer-агент:

> «Создай игру для детей 6–8 лет на изучение таблицы умножения, 20 уровней, 5 минут на сессию, без текста сложнее уровня Grade 2»

```yaml
game: multiplication-balloons
extends: tap-targets@1            # runtime/шаблон Balloon Pop
audience: { ages: [6, 8], readingLevel: grade2 }
locale: en-US
session: { targetMinutes: 5 }
mechanic:
  component: tap-correct-answer@1  # НОВЫЙ компонент: в Balloon Pop нет «правильного ответа»
  prompt: "{a} × {b} = ?"
  targets: { count: 4, distractors: nearby-products }
  wrongAnswer: gentle-shake        # no-lose, как в GDD
progression:
  levels: 20
  generator: multiplication@1
  schedule: [{ tables: [2, 5, 10] }, { tables: [3, 4] }, { tables: [6, 7, 8, 9] }, { mixed: true }]
rewards: { stickers: 20, perLevel: 1 }
theme: { background: sky, target: balloon, palette: default }
monetization: { ads: families-default, iap: [remove_ads] }
compliance: [google-families, coppa-2026]
```

Валидатор отклоняет спецификацию, если: строка UI сложнее Grade 2; touch-таргет < 64 dp; лимиты рекламы мягче `ADS`; оценка длительности сессии выходит за 5 ± 1 мин; компонент не зарегистрирован.

**API (минимум):** `validate(spec)` → ошибки с подсказками для агента · `build(spec, target: android|web|playable|scorm)` → артефакт · `qa(artifact, profile)` → отчёт · `package(artifact, store)` → листинг, скриншоты, Data safety draft. Публичный API для внешних клиентов (концепция 15) — только после доказанного спроса.

## 15. Risks

1. **Дистрибуция** (главный): органика ≈ 0 для средней игры.
2. **Платформенный/политический**: Repetitive Content, Families, бан аккаунта снимает весь портфель; изменения COPPA и Families (обновление 2026 года).
3. **Падение COPPA eCPM**: спрос на детский рекламный инвентарь сжимается.
4. **Коммодитизация**: AI-генерация игр и playables встраивается в сами сети (AppLovin, Meta, Unity) и в инструменты для учителей.
5. **Долг поддержки**: ежегодные требования × N приложений.
6. **Качество/репутация**: «AI slop» в детской категории — отзывы родителей и Teacher Approved важнее количества.
7. **Платежи и юрисдикция**: поддержка Казахстана для Play merchant и AdMob (проверить), налоги, договоры.
8. **Overengineering**: соблазн строить «свой Unity». Защита — правило из п. 16.

## 16. Unknowns и защита от overengineering

Неизвестно: реальная органика средней игры · реальный ARPDAU · CPI в детской категории · готовность B2B платить при бесплатных AI-инструментах сетей · наличие партнёров для малых языков · можно ли автоматизировать создание новых приложений в Play Console.

**Правило для каждой задачи:** «Какую бизнес-гипотезу это проверяет?» Если никакую из A–E — откладываем. DSL обобщается только после трёх реальных игр. API — после первого внешнего клиента. Платформа — после одной прибыльной линейки.
